# Part 1: Written summary

The Model Context Protocol and the Google Calendar MCP server

The Hugging Face article by Ksenia Se, "What Is MCP, and Why Is Everyone Suddenly Talking About It?" (March 2025), presents Model Context Protocol as an open standard which Anthropic released in November 2024 for connecting AI assistants to data and tools. Its central argument concerns the cost of integration. Before MCP every model-tool pairing required its own glue code, an M×N problem; with one shared protocol it turns into M+N, as any compliant client can work with any compliant server. The article also separates MCP from its neighbours. Agent frameworks such as LangChain decide when a tool gets used, whereas MCP standardizes how the tool is exposed and called. RAG supplies passive context, whereas MCP allows the model to act. It also lists limits: running many servers adds overhead, remote and multi-user use and security were still immature, and more tools do not guarantee better tool use, since descriptions matter.

In MCP terms the roles relate as follows. Host is the application the user talks to, such as Claude Desktop or my terminal agent. Inside the host, an MCP client keeps one-to-one connection with each server. The server wraps an external system and offers primitives: tools that the model can call, resources it can read and prompt templates. The client discovers them at runtime through tools/list, so the host does not need dedicated code for each integration.

The server I explored is nspady/google-calendar-mcp, a TypeScript project with about 1,200 GitHub stars. I chose it since my Action tool also writes to Google Calendar. Most of its 13 tools respect the principles from class. list-calendars, get-event and delete-event each perform one task, and the arguments are typed with zod schemas, most of them carrying a description. Several tools, however, bundle responsibilities. update-event handles field edits, three scopes for recurring events with arguments that become required only under certain scopes, conflict checking and Meet links inside one schema. manage-accounts adds, lists and removes accounts in a single tool, whereas list-colors returns different data depending on whether calendarId is passed. Behaviour is not always predictable either. create-events skips the duplicate and conflict detection which create-event performs. The authors seem aware of the cost, as ENABLED_TOOLS setting lets users hide tools to save context. Thus, the lesson I took for my own toolkit was to keep each tool narrow, typed and idempotent.
