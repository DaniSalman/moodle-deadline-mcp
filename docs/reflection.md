# Reflection

I started from the student's request, which is to read Moodle, put the deadlines in the calendar and get notified X hours before, and I asked myself which part of it changes something in the world. Reading Moodle changes nothing, so it became the Data tool, marked read-only so that the agent can call it freely. Writing into the calendar is the only side effect, so it became the Action tool. The hard part was the notification. A separate send_notification tool would have been a fourth tool, and it would have needed a process staying alive until the reminder time. Instead I realised that the reminder is a property of the calendar event; Google delivers the push itself, and the Action tool keeps one single effect. The Orchestration tool owns the loop of reading once and writing N times. Keeping this loop inside the server means one model decision instead of 1 + N tool calls, a fixed order and one report of what was created, what already existed and what failed. Two decisions made the tools predictable. Every event stores a dedupKey (the Moodle event UID), so running the sync again never duplicates anything. And every expected problem, such as an expired export link, a missing Google sign-in or a deadline that already passed, comes back as a clear ToolError with the fix in plain words instead of a silent failure.

For this use case three tools felt like the right number. Each tool corresponds to one sentence a student would actually say ("what is due", "add this one", "sync everything"), and the agent never had to choose between tools that overlap. There are limits, though. The Orchestration tool repeats a path that the agent could also take with the two smaller tools, which is acceptable but gives two ways of doing the same job; moreover, recognising deadlines through fixed title patterns such as "is due" or "closes" can miss wording that some instructors use. The libraries are also moving fast (FastMCP 4 and version 2 of the MCP Python SDK renamed several fields), so many examples found online were already outdated. As next steps, I would add updating and deleting events when Moodle moves a due date, which needs a fourth tool and probably a confirmation step since it modifies existing data. I would also run the sync on a schedule so it happens without asking, use MCP elicitation for confirming before writing, and host the server remotely with OAuth so it works from phone as well.
